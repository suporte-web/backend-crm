Fluxo implementado
Formulário do site -> POST /api/informativo (Next.js) -> POST /api/informativo/site (CRM) -> InformativoAssinante.
O módulo não depende de Leads, Entradas ou Solicitações do Site.
O nome é normalizado removendo espaços excedentes; o e-mail é convertido para minúsculas e tem espaços nas extremidades removidos.
O upsert pela chave única email impede duplicatas, atualiza o nome e reativa DESCADASTRADO para ATIVO.
O aceite omitido em um recadastro preserva o valor anterior. O formulário existente informa o aceite ao assinar; esse aviso foi preservado e o envio registra aceitePrivacidade=true.
Nenhuma alteração foi feita nas permissões das telas existentes. A nova tela registra sua própria chave informativo e respeita o bloqueio dessa chave.

Prisma
Enum StatusInformativo: ATIVO e DESCADASTRADO.
Model InformativoAssinante: id, nome, email único, status, origem, aceitePrivacidade, criadoEm e atualizadoEm.
Status inicial ATIVO, origem SITE_PIZZATTOLOG, datas automáticas e aceite padrão false.
Migration aditiva: cria somente o enum, a tabela e o índice único de e-mail. Migrations anteriores foram preservadas.
Executados: npx prisma validate, npx prisma generate e prisma migrate deploy (CLI local).
A nova migration já foi aplicada no PostgreSQL local crm_portal, localhost:5432.
Em outro banco/ambiente, executar dentro do CRM backend:
  npx prisma migrate deploy
  npx prisma generate
Não é necessário criar outra migration. Reiniciar o backend após mudar variáveis de ambiente.

Endpoints
Site: POST /api/informativo — valida o payload e chama o CRM server-side.
CRM: POST /api/informativo/site — exige header x-integration-token com SITE_LEAD_INTEGRATION_TOKEN.
CRM: GET /api/informativo — exige JWT válido e perfil ADMIN ou MARKETING.
Filtros da listagem: ?q=maria&status=ATIVO. q pesquisa nome/e-mail sem diferenciar maiúsculas; status aceita ATIVO ou DESCADASTRADO.
Formato da listagem: { assinantes: [...], totais: { total, ativos, descadastrados } }.
Os totais são gerais e não mudam com os filtros. Registros ordenados por criadoEm decrescente.
O cadastro retorna HTTP 200 com confirmação amigável, também para e-mails já cadastrados.
Erros internos não são repassados ao visitante.

Tela do CRM
Marketing -> Informativo Pizzattolog
Rota: /marketing/informativo
Cards de total, ativos e descadastrados; pesquisa e filtro; tabela no desktop e cartões no mobile.
Datas no formato dd/MM/yyyy HH:mm, fuso America/Sao_Paulo. Status com Chip e origem Site Pizzattolog.

Como testar manualmente de ponta a ponta
1. Iniciar CRM backend com npm run dev (3001), CRM frontend com npm run dev (3000), site backend com npm run dev (3003) e site frontend com npm run dev (3002). Se já estiverem em execução, reiniciar somente os processos que precisarem recarregar variáveis.
2. Abrir http://localhost:3002 e preencher Nome e E-mail em Informativo Pizzattolog. Clicar Assine. O botão deve mostrar Enviando..., ficar desabilitado e apresentar sucesso; os campos devem ser limpos.
3. Entrar no CRM em http://localhost:3000 com perfil ADMIN ou MARKETING. Abrir Marketing -> Informativo Pizzattolog ou http://localhost:3000/marketing/informativo.
4. Conferir nome, e-mail em minúsculas, status Ativo, origem Site Pizzattolog e data. Pesquisar por nome/e-mail e filtrar Ativos ou Descadastrados.
5. Reenviar o mesmo e-mail no site, inclusive com letras maiúsculas. Deve retornar sucesso e manter um único registro, atualizando o nome.
6. Para testar reativação, alterar apenas um assinante de teste para DESCADASTRADO via Prisma Studio (npx prisma studio), então reenviar o mesmo e-mail pelo site. Deve ficar ATIVO e manter ID e data inicial.
7. Confirmar que o e-mail de teste não apareceu como Lead ou Solicitação do Site.
8. Testar nome vazio/e-mail inválido e falha de conexão: deve aparecer mensagem amigável, sem dados técnicos. Uma tentativa que falhar deve preservar os campos.
